# Forest Pack: items, custom edits, library presets and list checks

Added on 2026-10-06, from a live study of Forest Pack Pro 9 in a scratch 3ds Max 2026 with centimetre units (`Forest_Pro.version()` = 900 is an API number: Forest Pack 9.4.3 returns it too). The original changes were Python only. The 2026-10-14 controller repair and curve-slot guard require the updated native bridge; see [deployed verification](forest-effects-verification-2026-10-14.md).

## Why

The existing `scatter_forest_pack` returned success for scatters with no items. Its `density` parameter wrote `maxdensity`, which is a cap and no density, and its "up" facing mode aligned items to the surface normal. Agents also had no way to read item positions, edit items, place library presets or find out why a forest was empty. Presets merged by hand gave 0 items.

## What changed

**`scatter_forest_pack` (fixed):**
- Density now sets the tile size, `units_x`/`units_y`. `density` is a percentage of `density_units_x_cm`/`density_units_y_cm`: 100 keeps them, 200 gives twice the items. The new `items_per_m2` sets both to 100 × √(1437 / items_per_m2) cm.
- `facing_mode` 0 or `"normal"` writes `direction = 0` (surface normal); 1 or `"up"` writes `direction = 100` (world up). It used to write 1 for "up".
- It uses the minimal verified recipe: `surflist`, the one Surface Area set active, `namelist`, `conamelist`, `cobjlist`, `geomlist = 2`, `problist`, and width/height from each source's bounding box (height is now the real height).
- It builds the forest and returns the real `count`, an `estimated_count` and the surface area. A scatter with 0 items fails with `ZERO_ITEMS`; the object stays in the scene for inspection.
- Inputs are validated in Python first; the object is created in one undo step and gets a unique name. It returns a dict, not a JSON string.

**New tools** (module `maxmcp/tools/forest.py`, helpers in `maxmcp/helpers/forest.py` and `forest_library.py`):
- **`forest_items`** (read only) pages through items: pivot `position`, an instance-ready `transform`, `geom_id`, `size`, and optionally `item_name`, `source`, `rotation_z`, `scale`, `seed`. It builds the forest first and returns world space unless `space="object"`. `refresh_surfaces` pulses `surfanim`.
- Legacy native controller-bound Forest Effect parameters at a nonzero timeline frame produce `CONTROLLER_ANIMATION_UNVERIFIED`. Migrate scalar bindings with `forest_effect_parameters(action="repair_animation")` and a fresh effects token; the numeric expression driver references the original controller and samples the current frame. New scalar bindings/imports use this route. Curve-bearing item reads validate native slots before building; malformed row/slot states return `CURVE_STATE_INVALID` instead of entering the known crashing path.
- **`forest_edit_items`** moves, deletes, creates and resizes items, and sets rotation (the final angle, random rotation included), seed or item type. A procedural forest is refused unless `allow_custom_edit=true`, which builds it and switches it to custom edit first. Forest Pack doesn't record item edits in undo, so the result gives `undoable` (true only when the call switched the forest to custom edit) and `revert`, an edit list that puts the items back. Created items that lie off every surface are reported.
- **`forest_set_mode`** switches between `procedural` and `custom_edit`. Going back to procedural needs `confirm_discard=true`.
- **`forest_instances`** turns a scatter into real scene nodes, like Forest Tools' Instantiate button (which has no
  MAXScript). It builds the forest and creates one node per item in the same call (the build reorders items, so
  transforms are never taken from an earlier read), with the exact transform `forest_items` reports, on a layer
  (default `<forest>_instances`), in one undo step. `mode` is instance, copy or reference. Nodes are unparented,
  ungrouped (a closed-group source would otherwise clone its whole group), unhidden, unfrozen and tagged for the
  forest, so `action="count"` and `action="delete"` (with `confirm_delete=true`) find exactly them. Billboards,
  disabled items, group-head and missing sources are skipped and counted. Refused before anything is created:
  Reference-mode forests, empty forests and more items than `max_items` (1..10000). Over Max Items Viewport,
  Forest Pack keeps every k-th grid cell, so a thinned build lands far below the cap (354 items with the cap at 353
  gave 89); the build therefore runs with `vmaxitems` raised to 8 x `max_items` and restored afterwards, also on
  failure, and a thinned probe build trips `ITEM_LIMIT` instead of yielding a partial set. It reports `FOREST_COLOR_TINT_LOST` when Forest Color is in the materials and
  `EFFECTS_SNAPSHOT` when effects are on; render-time behaviour such as Edge mode isn't checked.
  Unit-tested; tested live on throwaway Max 2027 (Forest Pack 9.4.3): instances sit exactly at the `forest_items` transforms, are unparented, ungrouped, visible and on their layer; a second run gets a new prefix; `ITEM_LIMIT` creates nothing; delete removes exactly the tagged nodes; `disable_source` works; a Checker / Multi/Sub source works and Forest Color is reported through it; with `vmaxitems` below the item count every item is created and the cap is restored, also when `ITEM_LIMIT` refuses. Confirmed live by the MCP issue fixes session on the 1.7.5-based fork (36/36 checks, 2026-10-14); a rerun on the 1.7.6 merge is pending.
- **`forest_library`** (Python only) searches every library `index.xml`: presets, 3D items, 2D billboards and Forest Ivy items. Every kind is searched by default (`kind="all"`); each item says whether `forest_from_library` can place it (`placeable`). Each root gets 10 s; a slow share returns what it found, with an `error` on that root. Scans are cached for 5 minutes (1 minute for a root that didn't answer).
- **`forest_from_library`** places a preset or 3D item on surfaces, with optional include/exclude splines and a material library swap. It reads back the merged forest's translation toggle and X/Y/Z extents and warns when translation is enabled with active spline areas. Forest Pack can still move item pivots outside include splines or into exclude holes. It fails with `ZERO_ITEMS` when nothing is scattered; the nodes stay, and the error's details list them in `remove_with`. Merging a library file clears 3ds Max's undo history, so it needs `allow_undo_flush=true`, and the placement can't be undone: the result gives `undoable: false`, `undo_history_cleared: true` and `remove_with`, the nodes to delete to take it out again.
- **`forest_validate`** checks the item and area lists, builds the forest and reports the count. `fix=true` makes conservative repairs.

## Fixes from the iToo docs review (issue #24, 2026-10-11)

The iToo docs review (`itoo-docs\README.md` on the dev share) raised five Forest Pack problems. Each was probed live in a scratch Max 2027.2 with Forest Pack 9.4.3 (`version()` 900); the probe scripts and outputs are in `livetests-2027\runs-1011\probe-fp\`.

**Density, and what `count` is.**
- Items per tile are the white pixels of the stock map, `dense.bmp` (1437), so the full scatter is about 1437 × area / tile (22992 = 16 × 1437 at 250 cm tiles on a 10 m plane). Writing `threshold` or `mapname` doesn't change the stock map: it is binarised when the forest is created. `threshold` applies only to a texture in `distmap` (the custom distribution map). `lock_ratio` on uses `units_x` for both sides; a new forest has it on, so `scatter_forest_pack` turns it off for unequal units.
- `count` is `trees.count()`, the viewport build. Over "Max items Viewport" (`vmaxitems`, 50000 by default; 0 = no limit) Forest Pack keeps 1 in k grid rows and columns, k = ceil(√(N / vmaxitems)): 100 cm tiles on 100 m² gave 35800 of 143700, which the 2026-10-06 notes took for saturation. `forest_items` and `trees.*` read that thinned build; the render keeps every item up to "Max items Render" (`rmaxitems`, 1 M).
- `maxdensity` caps the candidate cells (white and black map pixels, `pixels_x` × `pixels_y` = 10000 per tile) in millions, 40 by default, 0 = no cap. Over it Forest Pack scatters **0 items**: 1.11 M cells with `maxdensity` 1 gave 0, 1.0 M gave 143700.
- **Now** `scatter_forest_pack` reads `vmaxitems`, `rmaxitems`, `maxdensity` and the map's pixels back and returns `limits`, `viewport_thinned`, `estimated_viewport_count` and `count_is_viewport_build: true`; `estimated_count` stays the full scatter. It warns `VIEWPORT_LIMIT` when the estimate is over `vmaxitems` and the count agrees with the predicted thinning (a thinned build never holds more than `vmaxitems` items, so a count over it is never called thinned; see the review fixes below), `MAXDENSITY_CAP` when the count is 0 (and names it in `ZERO_ITEMS`) and `RENDER_LIMIT` (over `rmaxitems`; per the docs the render then shows nothing). The old "very small density tiles saturate" warning is gone. `forest_validate` does the same from the forest's own settings, takes `lock_ratio` into account, leaves out gap items' share, and returns `limits`. `forest_items` (procedural mode) and `forest_from_library`, which have no estimate, add the note `VIEWPORT_LIMIT_POSSIBLE` when the count lies between a quarter of `vmaxitems` and `vmaxitems`.
- Live check: 100 cm tiles on a 10 m plane gave `count` 35800, `estimated_count` 143700, `viewport_thinned: true`, `estimated_viewport_count` 35925; `forest_validate` agreed. With 95 cm tiles and `maxdensity` 1 the forest built 0 items and `forest_validate` named the cap.

**`direction` runs from -100 to 100.** -100 points items world down, 0 along the surface normal, 100 world up (live, on a plane tilted 30°). `scatter_forest_pack` takes `direction` (-100 to 100), which overrides `facing_mode`; `facing` is then `"down"`, `"normal"`, `"up"` or `"custom"`. It reads `direction` back and warns `DIRECTION_NOT_APPLIED` if it differs, naming "Scale to fit sloped areas", which forces it to 0. Live: `direction=-100` gave items whose Z axis points down.

**Exclude areas and translated items.** A spline exclude cuts only the include splines listed before it (a lower index in the area lists); the Surface Area is cut wherever the exclude is listed. `forest_from_library` appends include splines, then excludes; `forest_validate` warns `EXCLUDE_BEFORE_INCLUDE` if an active exclude precedes an active include. Separately, with `applyTranslation` on and nonzero X/Y translation extents, Forest Pack 9.4.3.766 moved pivots outside an include spline and into an exclude hole in live Max 2027 tests, under both Point and Size boundary checks. The validator therefore emits `TRANSLATION_SPLINE_BOUNDARY` and reports the extents; `forest_from_library` returns the same translation readback and warning. `forest_settings` reports the extents read-only. The warning does not repair the scatter or guarantee renderer edge trimming; inspect `forest_items` positions and choose smaller X/Y extents or a tested effect/renderer workflow. The scratch test measured 0 crossings with translation off, 83 outside / 19–20 inside at ±20%, and 260–263 outside / 65–96 inside at ±200%. The translated placement was not made safe by Boundary Checking Point or Size. See issue #39 for exact evidence and limits.

**`geomlist` 0 is a gap.** A "Disabled" item takes its probability share of positions and places nothing there; `trees.count()` leaves those positions out (50/50 with a gap: 711 of 1437). Forest Tools' "Disable at end" writes it too. `forest_validate` now reports `GEOM_NONE` as a note, not an error, and scales the estimate by the share of items that place something. Live: 7952 items against an estimate of 7983, `ok: true`. A 0 that `fix=true` wrote itself is an error, `SOURCE_UNRESOLVED` (review fixes below).

**Default preset: not confirmed, so nothing is overwritten.** The docs say a "default" preset saved in Forest Pack (`forest_presets.ini`) changes every new Forest. No preset exists on this machine, and writing one to test it was off limits, so `scatter_forest_pack` doesn't pin the distribution settings: writing `mapname` wouldn't reload the map anyway, and clearing `distmap` was seen to make viewport thinning harsher for good. It reads them back instead and warns `NON_DEFAULT_DISTRIBUTION` (and leaves the estimate out) when the new forest doesn't use the stock map, and `DIRECTION_NOT_APPLIED` as above.

**Library paths** with a leading backslash resolve against the index folder, and thumbnails are looked up in `thumbnails\` first, as for RailClone ([railclone.md](railclone.md#library-paths)).

**Review fixes (2026-10-11).** A review of the fixes above found four problems; each is fixed and unit tested, and the live checks ran in the scratch Max (`runs-1011\itoofix-r2\`).
- `forest_validate(fix=true)` pads a short `geomlist` with 0 where no source can be relinked by name. With `GEOM_NONE` now a note, the check after the fix said `ok: true` while two thirds of the positions were empty gaps the fix had made. **Now** a 0 the fix itself wrote is an error, `SOURCE_UNRESOLVED` ("link its source and set `geomlist` to 2, or remove the item type"), so `ok` is false. A chosen gap looks the same in the scene (`geomlist` 0, no source), so a later plain check reports it as a `GEOM_NONE` note, which now says how to fill it.
- `MAXDENSITY_CAP` ("Forest Pack scatters 0 items") was added whenever the summed candidate cells were over the cap, even next to a positive count. Live, two stacked 10 m planes at 100 cm tiles (2.0 M cells together) built 31990 items under `maxdensity` 1: the cap isn't applied to the sum of several surfaces, and it is all or nothing. **Now** `MAXDENSITY_CAP` is reported only when the count is 0 or unknown; with items it is the note `MAXDENSITY_SUM_OVER_CAP`.
- `viewport_thinned` was inferred from the estimate alone. The estimate can overshoot (the bounding box of a surface over 50000 faces; excludes and slope or altitude limits aren't counted), and a forest whose distribution map was assigned and cleared thins harder than predicted. **Now** a count is called thinned only when it lies within 25% of the predicted N/k²; otherwise `viewport_thinned` is null and the note `VIEWPORT_LIMIT_UNCERTAIN` says to count again with `vmaxitems` 0. `scatter_forest_pack` then also gives its "far fewer items than estimated" warning, which a thinned result suppresses.
- `scatter_forest_pack` wrote `units_x` and `units_y` but never `lock_ratio`, which a new forest has on, so `density_units_y_cm` did nothing while `items_per_m2_estimate` and `units_y_cm` reported it as applied. **Now** unequal units turn `lock_ratio` off before they are written; the result reports `lock_ratio`, and `units_y_cm` and `items_per_m2_estimate` describe the tile Forest Pack uses (`UNITS_Y_IGNORED` if the lock still reads on). Live: 300 × 600 cm tiles on a 10 m plane gave 8042 items (estimate 7983, `lock_ratio` false); locked, the same call gives about 16000.

## Reference mode and RailClone links (issue #27, 2026-10-11)

Forest Pack 9.4.1 added Distribute > Reference > "Use RailClone Items": a forest in Reference mode takes its item positions from the items a RailClone (7.3.2 or later) exports. This was probed live in a scratch Max 2027.2 with Forest Pack 9.4.3 and RailClone 7.3.5 (`livetests-2027\runs-1011\probe-26-27\`, p12-p22), and the fixes were checked through the tools ([Status](#status)).

**How the link works (live).**
- `distmode` 2 is Reference. With `distrefusercitems` true and the RailClone in `distrefnodes` (`distrefmode` 0), `trees.update()` places exactly the items the RailClone exports: 8 posts, 80 rails, or 80 pickets through a Transform. Such a forest needs no surface and no active area.
- Export to Forest on a Segment is only the per-segment array `sexportforest[k]`; the style XML doesn't change. On a Transform it is the XML parameter `<parameter id="export_forest" name="Export to Forest" value="1"/>`, which `setXMLStyle` accepts.
- Every failure is silent: no Export to Forest, Proxy Cache or a disabled RailClone give 0 items; with the RailClone's `autoUpdate` off the forest keeps the last build; with `distrefusercitems` off each RailClone is one marker at its pivot (1 item); an empty `distrefnodes` gives 0 items.
- A Tags operator's `fpgeom=<name>` reaches the output items as `tags="fpgeom=<name>"` and applies only with `distrefmatchname` on. It matches the Geometry List name (`namelist`), not the source object's name, and case doesn't matter: `fpgeom=P27_cyl` gave all 80 tagged pickets the item named `p27_CYL` (the 8 untagged posts were picked by probability). Items whose tag matches no name got item type 1.
- `isProperty forest #distrefusercitems` tells whether this Forest Pack has Use RailClone Items.

**`forest_validate` (fixed).** It reported `NO_ACTIVE_AREA` as an error on every Reference-mode forest, one that built 88 items included, and for an empty one it added `NO_ITEMS` with no cause.
- **Now**, with `distmode` 2, the area checks (`NO_ACTIVE_AREA`, `SURFACE_AREA_MISSING`, `SURFACE_LIST_EMPTY`, `AREA_NODE_MISSING`, `EXCLUDE_BEFORE_INCLUDE`) are notes, the estimate is left out with a note (one item per reference node, or per item each linked RailClone exports), and the candidate-cell cap isn't computed.
- It reads `distrefusercitems`, `distrefmatchname`, `distrefmode` and `distrefnodes` and, for each RailClone in the list, without a rebuild: `disabled`, `proxymode`, `autoUpdate`, how many segments have `sexportforest` on, how many Export to Forest parameters are on in `getXMLStyle` (never `getStyleDesc`, which empties the export until the next rebuild), the item count of its last `getXMLOutput`, and its distinct item `tags`, whose `fpgeom` names are parsed in Python. With a RailClone in the list it also reads the running RailClone version. The result adds `distribution: "reference"` and `reference` (settings, nodes, `rc_version`).
- Causes: `REF_NO_NODES` (no valid reference node), `RC_LINK_NO_EXPORT` (no segment and no Transform exports), `RC_LINK_PROXY_CACHE`, `RC_LINK_DISABLED`, `RC_LINK_EMPTY` (the last build has no items) and `RC_LINK_UNSUPPORTED` (RailClone before 7.3.2, or a Forest Pack without `distrefusercitems`) are errors when the forest builds 0 items, and warnings next to items from other nodes. `NO_ITEMS` names them in its detail and lists them in `causes`. Warnings: `RC_LINK_STALE` (`autoUpdate` off: the forest uses the last build), `RC_LINK_OFF` (Use RailClone Items off: one marker per RailClone), `FPGEOM_IGNORED` (`fpgeom` tags with Match by name off) and `FPGEOM_UNMATCHED` (a tag that names no Geometry List item, compared without case). Deleted entries in `distrefnodes` give the note `REF_NODE_MISSING`.

**`forest_items`** returns `reference` for a Reference-mode forest, read only: `use_railclone_items`, `match_by_name` and `nodes`, each with `name`, `handle` and `railclone`; a RailClone adds `exported_segments`, `transform_exports`, `proxy_cache`, `disabled` and `auto_update`.

## Verified Forest Pack facts

These were measured live; the tools rely on them.

**Building and reading**
- The item list is built lazily. `classOf` doesn't build it; `trees.update()` does (12–21 ms for 10–23k items). Every tool calls it before reading.
- `trees.*` indices are 0-based. `getGeomID` is 1-based into the item lists. Out-of-range reads return undefined or -1; out-of-range writes do nothing, without an error.
- `getPosition` is the 2-D distribution point (z is always 0). `getRotation` and `getSize` return stored per-item values; the random rotation and scale exist only in `getFullTransform`.
- Item data is in the forest's object space, relative to `node.objectTransform` (which includes the forest's own pivot offset).
- `getFullTransform i` maps the source object's *object-space* vertices. Its translation is not the item's pivot: for a source whose pivot is offset from its geometry it was 170 cm away.
- **srcOffsetTM** is the source object's pivot offset: `scaleMatrix objectOffsetScale * (objectOffsetRot as matrix3) * transMatrix objectOffsetPos`. An instance of the source placed at `inverse(srcOffsetTM) * getFullTransform i * forest.objectTransform` matched a mesh snapshot of the forest exactly (with the source's pivot moved, the source rotated 20° and the forest rotated 30° and moved). `forest_items` returns that matrix as `transform` and its translation as `position`.
- Forest Pack caches surfaces. After a surface moves, item Z changes only after a `surfanim` pulse (`surfanim = true`, `trees.update()`, back to false). Reassigning the same `surflist` doesn't refresh it.

**Density and lists**
- Density is set by `units_x`/`units_y`, the tile size: about 1437 items per tile with the default density map (`dense.bmp`'s white pixels). On a 10 m plane, 1000 cm tiles gave 1437 items and 300 cm tiles 16023. `maxdensity` caps the candidate cells, in millions; it had no effect from 1 to 1000 on 2026-10-06 only because those scatters stayed under the cap. 100 cm tiles on 100 m² gave `trees.count()` 35800, not 143700: that is the viewport Max Items limit, not saturation ([issue #24 fixes](#fixes-from-the-itoo-docs-review-issue-24-2026-10-11)).
- `namelist` is the master list. On a rebuild, Forest Pack pads every other item list to its length with 0, 0.0 or undefined; padded items silently produce nothing or empty items at the forest's origin. Nothing raises an error.
- `geomlist`: 0 = a gap ("Disabled": it takes its probability share of positions and places nothing), 1 = billboard, 2 = custom object from `cobjlist`. **3 crashed Max** (access violation) on a rebuild with no proxy, and that object never produced items again. No tool writes 3, and no tool rebuilds a forest whose `geomlist` holds anything but 0, 1 or 2 (`CRASH_RISK`).
- `direction` runs from world down (-100) through the surface normal (0) to world up (100). MAXScript doesn't clamp it. "Scale to fit sloped areas" (`scalelope`) forces it to 0, and it stays 0 after `scalelope` is turned off.
- The minimal working forest: `surflist`, `namelist`, `geomlist` (1 or 2), `pf_aractivelist = #(true)` and a tile size suited to the surface. `cobjlist` is needed for visible geometry. `arnodelist` isn't needed for the Surface Area.
- `pf_aractivelist` is the area "active" flag. Forest Pack always keeps one type-3 Surface Area entry and appends an inactive one when it is missing. Areas add up: the Surface Area plus an include spline gives double density inside the spline; an exclude spline (`arincexclist` 1) cuts a hole in the Surface Area wherever it is listed, but only in the include splines listed before it (a lower list index).

**Custom edit**
- Per-item writes work only in custom edit mode, `mode = 1`. In `mode = 0` every write is ignored.
- Switching to `mode = 1` freezes the items as last built; on a forest never built it froze an empty set. So the forest is built in mode 0 first.
- Setting `mode = 0` discards the edits for good; setting it back to 1 doesn't bring them back. Edits survive seed and tile changes, node moves, surface refreshes and save/merge.
- `setRotation` takes radians and only Z takes effect. The stored value is an offset **added** to the item's random rotation, so the final angle is random + stored: stored 0 gave 54.3°, stored 45° gave 99.3°. `forest_edit_items` stores the target minus the random part, so `rotation_z` is the final angle, and it sets rotations after the seed and item-type edits, which can change the random part. `setSize` takes absolute sizes `[w, w, h]`. `create p w h geomid` appends at index count−1 and projects onto the surface; a point off every surface is kept unprojected.
- Deletes shift the later indices down at once, so the tools delete highest first.
- With random translation on, a moved item's pivot lands off the requested point.
- World to object space: `p * inverse(forest.objectTransform)`.

**Library and presets**
- Library roots are listed in `HKCU\Software\Itoo Software\Forest Pack Pro\LibraryDir` (this machine has a local and a network root); the default is `%LOCALAPPDATA%\Itoo Software\Forest Pack Pro\lib`. `forest_library` scans every registry root and the default, each folder once. Each folder's `index.xml` lists `<item class="maxobject">` entries (`maxfile`, `object`, `matlib`, `material`) and `tree_billboard` entries (2D, with `<library>`). `$(LIBROOTPATH)` is the root; other relative paths are relative to the index folder, also with a leading backslash (`\objects\x.max`, the docs' template form; no real index uses it). A `<bitmap>` file name is in the index folder's `thumbnails\`.
- `forest_library` gives each item a `kind`: `presets`, `3d` or `2d` when a folder in its path relative to the root has that name, `ivy` for a Forest Ivy item, and `other` for everything else. The studio's CRGR root (folders Трава, Камни, Растения) and the stock `Samples\The3dGarden` items are `other` (23 items on 2026-10-11). The default `kind="presets"` used to hide them all; the default is now `all`, and results list exact matches first, placeable items before the rest.
- Forest Ivy items (`ForestIvy\Climbing Plants`, 30 items) are class `maxobject`, but their `<maxfile>` is an `.fp` file, Forest Ivy's own format (it starts `00 00 01 ff`, not the OLE header of a `.max` file). `forest_from_library` can't merge them.
- A library-level `<select setmacro="X">` list defines `$(X)` for its items. Stock example: `Presets\Autumn Leaves` (36 items) has `<object>_fp_L-GS-1g-$(PRESET_STATE)</object>` and `<material>_fp_leaves_$(PRESET_STATE)</material>`, with the options `clean` and `dirty`; the `.max` file holds `_fp_L-GS-1g-clean` and `_fp_L-GS-1g-dirty`. The catalogue expands such macros to the option marked `default="1"`, else the first option (here `clean`), in `object`, `material`, `maxfile` and `matlib`, and keeps the original in `object_template` and the values in `macros`. `$(RENDERER)` stays for `matlib_renderers`, and an option that calls a script (`@forestlib.ms:...`) is never used. Forest Pack's browser stores its last choice in `HKCU\...\Forest Pack Pro\LibraryMacros` (`preset_state=clean`); the catalogue doesn't read it.
- Merged alone, a preset's `cobjlist` and spline `arnodelist` entries come back undefined. `conamelist` names the source objects (`namelist` is only a label and can be in another order).
- Merging the forest and its sources in **one** `mergeMAXFile` call relinks `cobjlist`, even when Max renames a duplicate. Merging them in two calls and wiring by name broke when Max renamed `_fp_wildgrass_09` to `_fp_wildgrass_001`.
- **Stock presets ship their Surface Area inactive.** That is why a retargeted preset gave 0 items. Activating it gave 23473 items on a 10 m plane.
- `loadTempMaterialLibrary` loads a `.mat` (about 0.4 s for 24 materials). Replacing `matList[i]` with the library material of the same name makes Forest Pack rebuild its `forest_automat_*` Multi/Sub.

**Export**
- `Forest_Pro.ForestPack.exportData file fields` is class level (`node.ForestPack` doesn't exist). It always writes **every** forest in the scene, whatever is selected, hidden or disabled: 82 MB for 12 forests. No tool uses it; `forest_items` reads one forest through `trees.*`.

**Undo** (verified in the live test of 2026-10-06, on Max 2026)
- Merging a library `.max` file clears 3ds Max's whole undo history. This holds for Forest Pack items and RailClone items alike.
- `mergeMAXFile` is never recorded in undo, even inside `theHold`.
- `loadTempMaterialLibrary` also clears the whole undo history. Inside an open `theHold` step it wipes that step.
- Forest Pack per-item edits (`trees.setPosition` and the other `trees.*` edits) are never recorded in undo. Changing `.mode` is recorded.
- **An undo crashed Max.** A draft of `forest_from_library` merged outside undo, then, inside an undo step, made copies of the merged nodes, pointed the copied forest's `cobjlist` from the merged originals to the copies (so the undo record held the originals as the old values), and deleted the originals with undo off. A later `max undo` crashed Max. The rule: never leave an undo record that refers to a node deleted with undo off. That draft was never committed; `forest_from_library` now puts nothing in an undo step.

**Testing undo.** Agents can't live-test undo: the user's rule is that agents never run `max undo` or `max redo` through MCP, because `max undo` followed by `max redo` crashed Max 2027. The tools' undo behaviour is therefore safe by construction (no undo step in `forest_from_library`; only the mode switch is recorded in `forest_edit_items`), and the unit tests check the generated scripts for it. Undo hasn't been run on the current versions of these tools.

**MAXScript pitfalls met in the live test**
- A `for ... collect` written straight into a function call's arguments that reads the caller's locals failed with "Bad free thunk local member index", or read the wrong variable (a loop index became the stringStream). The scripts collect into a local first, then pass the local (`fpKeepAreas`, the lists in `scatter_forest_pack`).
- Keywords can't be variable names: `local at = ...` was a parse error. It is now `atype`. The same goes for `by`, `to`, `on`, `in`, `of`, `do`, `as`, `max`, `set`, `tool`, `undo`, `from`, `with`, `where`, `while`, `collect` and the other keywords. Constants aren't reused as names either (`ok` is now `hasSrc`). The unit tests check every local, parameter and loop variable in the scripts against both.
- `getHandleByAnim` returns an IntegerPtr; `fpMark` and `fpNewNodes` convert it with `as integer64` before comparing.
- `intersectRay` with a ray origin at z = 1e7 missed a plane at z = 0 (float precision). The off-surface check in `forest_edit_items` starts its rays just above the surface's bounding box.

## How the tools work

**`forest_items`.** One script: build (and pulse `surfanim` with `refresh_surfaces`, outside the undo stack), count items per type, then return the page. Items whose type has no valid source return the raw item TM, flagged `no_source`. `limit` is at most 5000; a full transform costs about 100 bytes per item.

**`forest_edit_items`.** Python validates every edit (ops, keys, indices, sizes, seeds) and refuses an index both edited and deleted. In Max: refuse an open undo, a `geomlist` crash risk, an unknown mode, or a procedural forest without `allow_custom_edit`; check item types (1 or 2, with a source for 2) and indices against the built count. Then, in one undo step, of which only the mode switch is recorded: switch to custom edit if needed (and switch back without editing if the frozen count differs), read the state of every touched item (for `revert`), apply the edits except rotations, rebuild, set the rotations as final angles, delete from the highest index, create (a ray from just above each surface checks that the point is on one), rebuild, and set the created items' rotations. Edited and created items are read back with the stored point and the actual pivot.

`revert` deletes the created items, puts back the position, size, seed, item type and rotation of each edited item (at its index after the deletes), and creates the deleted items again at the end of the list. `undoable` is true only when the call switched a procedural forest to custom edit: undo switches it back, which drops every edit.

**`forest_from_library`.** Python finds the item by uuid, object (or its `object_template`) or English name. Items it can't place (2D billboards, Forest Ivy `.fp` items, items without a `.max` file or object) only match when nothing placeable does, so they never make a name ambiguous: on this machine `"Grass"` matched the CRGR preset and a stock 2D billboard, and now finds the preset. When several placeable items match, the `AMBIGUOUS` error lists each one's object and file and a key that finds it alone (its uuid, English name or object); a studio item has no uuid, and one stock uuid belongs to two items. An item that can't be placed fails with `UNSUPPORTED_ITEM`, before the consent check. Python then checks the file and the material library, and refuses the call unless `allow_undo_flush=true`, before anything is sent to Max. In Max:
1. With undo off, merge the object alone (the probe). A Forest object gives the source names from `conamelist` (falling back to `namelist`) that exist in the file, and the names of its spline areas, which are dropped. A plain mesh makes it a 3D item. The probe is deleted.
2. Merge the object plus its sources in one call, as before: no copies, no renames, no deleted originals. The merge has already cleared the undo history, so it and every step after it run with undo off, inside a `try` that also builds the report. On an error, every node created since the merge (a 3D item's new forest included) is deleted with undo off and the error is passed on. No undo record ever refers to these nodes. A 3D item becomes the only source of a new forest (`items_per_m2`, default 300 cm tiles).
3. Retarget: `surflist` = the surfaces; the area lists are cut to the Surface Area; it is active unless include splines are given; include splines are appended as active spline areas and exclude splines as active exclusion areas.
4. Optionally swap materials from the item library's `.mat` for `matlib_renderer` (presets: `matList` by name; 3D items: the `<material>` on the source). With `hide_sources` (the default), hide the merged sources. Build and return the count, the item types and their linked sources, the areas, the merged nodes and the materials swapped or missing, with `undoable: false`, `undo_history_cleared: true` and `remove_with` (the forest, then its merged sources): delete those nodes to take the placement out again.

Merges use `#autoRenameDups #useSceneMtlDups #neverReparent quiet:true`. The live recipe used `#useMergedMtlDups`; `#useSceneMtlDups` is used instead so a merge never replaces a material already in the scene (for example one converted for Vantage).

**`forest_validate`.** One read script collects the list lengths, every item and area entry, the surfaces (with their upward area) and the count; Python analyses them. Errors: an empty `namelist`, item lists shorter than `namelist`, `geomlist` 3 or another invalid value (the forest is then not rebuilt), missing sources, probabilities or sizes ≤ 0, unequal area lists, more than one Surface Area, no active area, an active spline area without a spline, an active Surface Area with no surfaces, missing surfaces, 0 items, and after a fix the gaps it had to pad (`SOURCE_UNRESOLVED`). Warnings: lists longer than `namelist`, short auxiliary lists, `conamelist` mismatches, a missing Surface Area entry, an exclude listed before an include it should cut (`EXCLUDE_BEFORE_INCLUDE`), translated items that can cross active spline boundaries (`TRANSLATION_SPLINE_BOUNDARY`), a tile too large for the surface, `VIEWPORT_LIMIT`, `MAXDENSITY_CAP` (count 0), `RENDER_LIMIT`, custom edit mode, disabled or manual update. It reports translation extents but does not change them or prevent the third-party boundary limitation. Notes: `geomlist` 0 gap items (`GEOM_NONE`), `VIEWPORT_LIMIT_POSSIBLE`, `VIEWPORT_LIMIT_UNCERTAIN` and `MAXDENSITY_SUM_OVER_CAP`. The estimate covers the Surface Area with the stock density map only, without the gap items' share; `limits` gives the caps, the candidate cells and whether `count` is thinned. In Reference mode (`distmode` 2) the area checks are notes, there is no estimate, and the same read script adds the reference settings and one row per reference node after the build ([issue #27](#reference-mode-and-railclone-links-issue-27-2026-10-11)).

`fix=true` pads short item lists (sources relinked by a unique matching name, `geomlist` 2 where a source exists and 0 otherwise, probability 100, size from the source's bounding box), relinks missing sources of type-2 items the same way, and pads short area lists with the defaults of a new spline area (inactive), in one undo step. A second script checks the lengths it read haven't changed (`STALE`), applies the plan and checks again. It never truncates a list (a long list may mean `namelist` lost an entry), never changes `geomlist` 3, and never activates an area. If a dialog in Max holds the first, read-only script of a `fix=true` call, the fix is never sent: the call fails with a retryable `BLOCKED_BY_DIALOG` that says nothing was fixed (`PrecheckBlocked` from `cb4d0ff`, as in `clone_objects`), so answer the dialog and repeat it. Without `fix`, or for a dialog during the fix itself, it's the usual `BLOCKED_BY_DIALOG`, which must not be repeated.

## Limits

- `forest_from_library` can't be undone, and it clears the undo history: delete the nodes in `remove_with` instead. Item edits aren't in undo either: pass `revert` back to `forest_edit_items`. Undoing a switch to custom edit sets `mode` back to 0, which discards the edits.
- Undo hasn't been run on the current versions of these tools (agents don't run undo; see "Testing undo" under [Verified Forest Pack facts](#verified-forest-pack-facts)).
- A forest whose `geomlist` holds 3 (perhaps valid with a proxy) is refused by every tool that rebuilds it.
- Indices in procedural mode change when the forest rebuilds.
- Include splines with the Surface Area inactive were verified with the spline at the surface's height only.
- 2D billboard and Forest Ivy (`.fp`) items can't be placed. `matlib_renderer` refuses `.pmat` material libraries.
- Items with library macros get the default option only: Autumn Leaves places its `clean` variants; the `dirty` objects can't be chosen.
- The library roots come from the registry as this server sees it. Under Claude Desktop's MSIX package that is a private copy of HKCU, which doesn't follow the real hive 3ds Max reads, so a root changed in Forest Pack's browser can be missing or stale in `forest_library`. `forest_from_library` merges by absolute path and doesn't need the browser's roots.
- 3D library items get Forest Pack's default viewport mode; the presets use `vmesh = 3`, which shows no meshes in viewports (not an error).
- The density estimate assumes the stock density map and counts the Surface Area only. Whether `count` is thinned by the viewport limit is told from that estimate, and only when the count agrees with it (within 25%; otherwise `VIEWPORT_LIMIT_UNCERTAIN`); without one (a preset's own map, a 3D item in `forest_from_library`, `forest_items`) it is only `VIEWPORT_LIMIT_POSSIBLE`.
- How the viewport limit meets custom edit mode (does a switch freeze the thinned build?) wasn't tested.
- A default preset saved in Forest Pack (`forest_presets.ini`) wasn't tested: none exists on this machine. `scatter_forest_pack` reads the distribution settings back and warns, but doesn't overwrite them.
- Reference mode: `RC_LINK_UNSUPPORTED` is unit tested only (no RailClone before 7.3.2 or Forest Pack before 9.4.1 at hand). The link checks read each RailClone's last build without rebuilding it, so after a script called `getStyleDesc()` its output reads empty (`RC_LINK_EMPTY`) until the next rebuild. Whether Reference mode projects items onto `surflist` wasn't tested, so a deleted `surflist` entry stays an error (`SURFACE_MISSING`). At most 500 reference nodes and 50 distinct tag values per RailClone are read (`nodes_truncated`).
